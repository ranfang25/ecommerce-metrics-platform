# 电商用户转化分析与指标管理平台

版本：实施计划 v1.0｜更新日期：2026-11-10｜状态：待实施

本 README 是项目执行与验收方案。下文中的功能数量、时长和性能数字是计划或验收目标；数据规模、分析发现和效果需要运行后填写。本文尚不代表产品已开发完成。

## 1. 项目目标

构建可操作、可复算、可排查异常的电商分析平台，贯通业务问题界定、需求拆解、指标设计、数据建模、分析拆解、页面实现、验收与迭代。

使用场景中的业务角色为模拟角色，公开样本为分析对象。实际试用、反馈与修改单独记录；本地样本分析不代表生产环境运营或商业效果。

平台围绕经营概览、转化诊断、用户分层及指标治理四类任务组织功能。

## 2. 业务问题与使用场景

核心问题：当访问量、购买转化率和成交金额出现不同方向的变化时，业务如何找到变化发生在哪个环节、哪个客群或设备维度，并检查是否源于数据异常？

这是假设分析任务，不预设样本一定出现“访问增长、成交下降”。先完成数据探索，再选择真实存在且样本足够的比较区间。

| 模拟使用者 | 要完成的任务 | 产品交付价值 |
| --- | --- | --- |
| 业务负责人 | 查看表现、比较两个完整周期、找到主要变化维度 | 在同一页面获得可追溯的指标与拆解结果 |
| 运营人员 | 定位浏览、加购、结账、购买中的损失环节 | 下钻到设备或客群，导出进一步核查的汇总数据 |
| 分析人员 | 明确分子分母、统计范围与数据来源，复算数字 | 搜索指标字典，查阅 SQL 和口径版本 |
| 数据产品维护者 | 检查刷新是否成功，定位异常，修复并重新验收 | 查看质量报告、任务日志、问题记录及版本 |

项目北极星验收问题：一个第一次使用产品的人，能否独立完成“查指标—看口径—找异常—看证据—导出结果”这条任务路径？

## 3. 范围与优先级

### P0：必须交付的最小可用版本

- 1 份 PRD，包含问题、用户任务、范围、优先级、功能规则和验收条件。
- 12 个核心指标，统一登记定义、公式、粒度、过滤条件、来源和版本。
- 4 个可操作页面：经营总览、转化诊断、用户分层、指标与数据运营。
- SQL 数据模型、自动化数据处理、数据质量检查与运行日志。
- 1 份业务分析报告，包含 3 条有 SQL 和图表支撑的发现，以及对应建议或待验证假设。
- 至少 20 条质量与一致性检查、10 条业务验收用例。
- 3 个受控异常案例、1 次修复后复跑的完整记录。
- 1 次真实试用走查；如暂时没有外部试用者，明确标记“技术验收完成，用户验证待完成”。
- 可复现运行说明、演示录像、版本说明和局限性说明。

### P1：P0 完成后选做

- D7 回访、窗内复购、简化 RFM；先验证完整观察窗口与样本量。
- 指标口径变更演示：修改申请、影响分析、版本升级、历史结果比较与回滚。
- 角色权限策略演示：业务查看、分析导出、维护管理；需要后端检查和越权测试。
- 第二轮真实试用、导出模板优化、查询耗时与人工操作耗时对比。

### P2：本次不作为完成条件

- 企业级单点登录、真实客户数据接入、分布式调度平台和实时计算。
- 自动改价、自动投放、在线推荐或实际运营干预。
- 大模型问数、复杂预测模型及微服务拆分。

先完成一个口径清楚、能解释和能验收的产品。加入 AI 功能时，也应先明确它解决的用户任务及额外验收成本。

## 4. 数据源与获取策略

采用 Google 官方 GA4 电商公开样本：

`bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`

官方列出的样本区间为 2020-11-01 至 2021-01-31。该数据经过脱敏，包含占位值，内部一致性存在限制，也不能与在线 GA 演示账户直接对账。[官方样本说明](https://developers.google.com/analytics/bigquery/web-ecommerce-demo-dataset)

可以通过 BigQuery Sandbox 查询公开数据；它有功能和资源限制，执行前检查账户状态、查询扫描量和配额。[Sandbox 说明](https://docs.cloud.google.com/bigquery/docs/sandbox)

执行顺序：

1. 查询实际表结构、日期覆盖、事件名称、参数名称和空值情况；历史样本未必包含最新文档中的全部字段。
2. 先用固定 7 天小样本验证链路，再扩展到完整区间。
3. 按日期和明确字段提取到本地 Parquet；避免每次启动页面都扫描云端原始事件。
4. 记录提取 SQL、日期范围、导出时间、文件校验值、源记录数、字段列表和运行版本。
5. 生产展示使用官方样本快照；故障演示和自动化测试使用另行标识的受控样本。
6. 事件总量、有效用户数、会话数、交易数均以 profile 报告为准，不提前写成“百万级”。

待生成：`reports/data_profile.md`、`data/manifest.json`。

可以先在 BigQuery 执行以下只读探查，核对 7 天内的事件分布；这里的数字仍以实际查询结果为准：

```sql
SELECT
  event_name,
  COUNT(*) AS event_rows,
  COUNT(DISTINCT user_pseudo_id) AS observed_user_ids,
  COUNTIF(user_pseudo_id IS NULL) AS missing_user_rows
FROM `bigquery-public-data.ga4_obfuscated_sample_ecommerce.events_*`
WHERE _TABLE_SUFFIX BETWEEN '20201101' AND '20201107'
GROUP BY event_name
ORDER BY event_rows DESC;
```

原始文件默认不提交 GitHub；提供数据获取方法、小型测试样本及来源说明。不要将个人 Google 认证文件、令牌或本机路径写入仓库。

## 5. 技术方案与产品边界

推荐实现路线：BigQuery 提取公开样本 → Parquet 快照 → DuckDB / SQL 建模 → Python 校验与任务编排 → Streamlit 产品界面。

这一路线可以在 Windows 和 macOS 上完成。Power BI 可作为 Windows 下的展示补充，不作为跨平台复现的前置条件。

| 组件 | 承担的工作 | 选择理由 |
| --- | --- | --- |
| BigQuery | 数据探查、筛选、嵌套字段提取 | 与官方样本保持来源对应 |
| DuckDB | 本地明细、会话、交易和汇总表计算 | 降低部署负担，保留 SQL 能力证明 |
| Python | 文件处理、任务编排、校验报告、日志 | 将数据链路变为可重复执行的流程 |
| Streamlit | 筛选、下钻、字典、质量状态和导出 | 形成能实际操作的演示产品 |
| YAML / CSV | 指标注册、规则、配置 | 将口径与业务规则从页面代码中分离 |
| Git | 需求、代码、问题、版本记录 | 展示从设计到发布的过程证据 |

建议数据链路：

```text
官方事件快照
  → 原始层：保留字段与来源
  → 事件 / 会话 / 交易模型：统一粒度与口径
  → 指标汇总与用户分层
  → 质量检查通过
  → 发布本次可用结果
  → 产品页面 / 汇总导出 / 周期报告
```

页面读取已验证的结果。处理失败时保留上一版成功结果，显示“刷新失败”和上次成功时间，避免展示半更新的数据。

## 6. 指标体系与数据口径

以下为建议的 12 个核心指标。正式实现前，为每一个指标完成注册和人工复算。

| 编号 | 指标 | 建议口径与边界 |
| --- | --- | --- |
| M01 | 观察用户数 | 选定事件日期内有效 `user_pseudo_id` 去重；它是匿名标识数，不等于真实人数或 GA 活跃用户 |
| M02 | 有效会话数 | 按会话开始日期筛选，使用用户标识与会话 ID 组合去重；缺失组合单独报告 |
| M03 | 商品浏览会话数 | 有效会话中出现 `view_item` 的会话数 |
| M04 | 加购会话数 | 有效会话中出现 `add_to_cart` 的会话数 |
| M05 | 结账会话数 | 有效会话中出现 `begin_checkout` 的会话数 |
| M06 | 购买会话数 | 有效会话中出现可识别购买事件的会话数；不与有效交易数混用 |
| M07 | 有效交易数 | 按购买日期统计有效交易 ID；重复冲突、缺失 ID 与隔离记录另列 |
| M08 | 已记录购买金额（USD） | 对同一有效交易集合汇总可用的 USD 购买金额；显示金额覆盖率，不称净收入或利润 |
| M09 | 金额完整订单客单价 | M08 / 有金额的有效交易数；分母与金额范围一致，缺失金额不补零 |
| M10 | 会话购买转化率 | M06 / M02；使用同一会话日期及筛选口径 |
| M11 | 浏览到加购转化率 | 严格有序漏斗中完成加购的会话 / 进入浏览阶段的会话 |
| M12 | 结账到购买转化率 | 同一严格有序漏斗内完成购买的会话 / 到达结账阶段的会话 |

用户与订单、事件与会话使用不同日期口径时，页面和导出必须注明。不要将不同分母拼成一个看似连贯的漏斗。

指标字典至少包含：`metric_id`、名称、业务解释、公式、分子分母、粒度、时间字段、过滤条件、可用维度、来源表、SQL 路径、异常处理、责任角色、版本、生效时间、验收用例。

去重用户数与会话数不能随意跨维度相加；周期转化率应由对应周期的分子分母重新计算，不能直接平均每天的转化率。用户级设备筛选采用“在选定设备上有符合条件事件”的明确口径，因此多设备用户可能同时出现在多个分组中。

新版本发布前，逐一确认：同名指标的 SQL、页面、导出和文档是否一致；有差异时，记录口径变更或已知限制。

## 7. 最容易出错的数据细节

### 7.1 会话、时间和历史样本

- 会话键使用 `user_pseudo_id` 与 `ga_session_id` 的组合。Google 官方也建议组合用户标识和会话 ID 以区分会话。[会话说明](https://support.google.com/analytics/answer/9191807?hl=en)
- 缺失会话 ID 的事件保留在原始层，排除出会话指标并显示排除占比。
- 明确 `event_date` 与时间戳的含义及项目使用的时区；日期筛选不要静默混用 UTC 与原站点日期。
- 会话跨午夜时，项目统一按该会话最早可见事件日期归属，并注明与其他工具可能存在差异。
- 以样本内指定日期作为“截至日期”；不使用本机今天计算旧样本的回访、分层或新鲜度。
- 历史按日重放只是演示增量处理，不称为真实每日产生的新业务数据。

### 7.2 事件与交易去重

- 不把“相同用户、事件名、时间戳”直接当成重复事件；同时间戳可能对应不同有效事件。
- 同一快照重复导入通过文件清单、分区覆盖和幂等控制解决，不依赖删除相似业务记录。
- 购买事件按交易 ID 检查重复。重复交易金额或归属冲突时记录、隔离并说明处理规则，不直接任意取第一条。
- 缺失交易 ID 的购买事件单独计数，不自动生成新 ID 后混入有效交易指标。

### 7.3 嵌套字段、关联与金额

- 参数和商品是嵌套、可重复结构；抽取参数与展开商品分别建模，防止两个数组同时展开导致记录和金额成倍放大。[导出字段说明](https://support.google.com/analytics/answer/7029846?hl=en)
- 事件、会话、交易和商品表各自声明粒度、键和关联关系；按设备分析交易时先得到唯一会话属性，避免多对多关联。
- 金额采用固定币种及明确精度；订单金额与商品明细金额分别验证，不假设二者天然完全相等。
- 有购买金额不代表存在成本和投放费用。没有相应字段时，不计算毛利、利润、获客成本或 ROI。
- 退款、税费、运费是否充分可用，先检查数据再决定；未验证前只展示“已记录购买金额”。

### 7.4 漏斗、用户分层与分析结论

- 主漏斗为同一会话内 `view_item → add_to_cart → begin_checkout → purchase` 的有序闭合漏斗。事件语义参照官方电商事件说明，实际事件可用性仍以样本为准。[电商事件说明](https://developers.google.com/analytics/devguides/collection/ga4/ecommerce)
- 每一步取前一步之后的最早有效事件；有重复浏览和多次加购时，保持同一套匹配规则。
- 时间戳相同且缺少可靠顺序字段时，标记为顺序不确定，单列覆盖率；严格漏斗不凭空确定先后。
- 未进入完整漏斗的购买可能来自路径不同或埋点缺失；开放事件统计与闭合漏斗分开展示。
- 用户分层使用截至日期前的行为；“窗内首购 / 窗内复购”不能宣称是生命周期首购或终身价值。
- D7 回访只计算具备完整 7 天观察期的人群；短观察窗口用户不按未回访处理。
- 渠道若仅能取到首次获客来源，就标注“首次获客来源”；不冒充当前会话渠道或因果归因。
- 比较完整且可比的日期区间，标注周末与节假日影响、小样本和未知维度。
- 数据中观察到的差异属于关联或贡献拆解；是否能改善转化，需要后续真实实验验证。

## 8. 数据模型与服务接口

建议模型最小集合：

| 模型 | 粒度 | 主要作用 |
| --- | --- | --- |
| `raw_events` | 原始导出记录 | 保留来源、提取版本和原始字段 |
| `fact_events` | 标准化事件记录 | 统一参数、日期及质量标记 |
| `fact_sessions` | 用户 × 会话 ID | 会话日期、设备、事件阶段与漏斗时间 |
| `fact_orders` | 有效交易 ID | 交易时间、金额完整性与冲突标记 |
| `fact_order_items` | 交易 × 商品行 | 商品分析，避免重复汇总订单金额 |
| `mart_daily_metrics` | 日期 × 已批准维度 | 页面指标和周期比较 |
| `mart_funnel` | 日期 × 维度 × 阶段 | 有序漏斗及覆盖率 |
| `mart_user_segments` | 用户 × 截至日期 | 窗内用户分层 |
| `ops_quality_results` | 运行 × 检查项 | 质量与对账结果 |
| `ops_pipeline_runs` | 每次运行 | 状态、时效、版本和数据区间 |

先用参数化查询函数作为数据服务，无需为每张表单独开发网络 API。页面、导出和报告调用相同的指标服务，避免维护多套公式。日期、维度、排序及导出字段使用明确的允许列表。

权限矩阵作为 P0 设计产物；真正的角色权限演示属于 P1。仅在前端隐藏按钮、增加“角色切换”下拉框，不能称为实现了鉴权。

## 9. 四个页面的产品要求

### 页面一：经营总览

- 展示用户、会话、有效交易、已记录购买金额、客单价、购买转化率。
- 支持完整周期对比，给出绝对变化与相对变化，基期为零时不显示无穷增长率。
- 支持设备及数据验证后可用的来源维度筛选；缺失值显示为“未知”。
- 指标点击可查看定义、日期口径、金额覆盖率、版本及数据源。
- 明确标注“历史样本”“样本截至日期”“上次处理成功时间”。

### 页面二：转化诊断

- 展示闭合漏斗、阶段转化率、样本量、顺序不确定和无法匹配占比。
- 支持设备及窗内用户分组比较，显示小样本提示。
- 提供两期差异及候选影响维度，附可点击的 SQL / 复算结果。
- 建议由分析证据支持，并将“已观察事实”和“待验证原因”分开。

### 页面三：用户分层

- P0 使用窗内未购买、单次购买、多次购买三类互斥分组。
- 展示人数、占比、记录金额和转化差异，说明截至日期及观察窗口。
- 同一时间范围内分层人数能够核对回符合该口径的总用户集合。
- P1 增加回访、复购或 RFM 时，解释观察窗口、阈值依据和样本不足问题。

### 页面四：指标与数据运营

- 可搜索的指标字典、指标版本、来源与 SQL 路径。
- 本次运行状态、上次成功版本、质量检查结果及已知问题。
- 可查看缺失值、重复交易、金额冲突、数据断档等问题样例。
- 支持展示一个问题从发现、定位、处理、复验到关闭的过程。

所有页面都要设计：加载中、无数据、数据不完整、处理失败四种状态。导出附带筛选条件、口径版本、数据范围与生成时间。

## 10. 实施流程与阶段交付

预估总投入为 50–70 小时，约 10–14 个有效工作日。已熟悉 SQL、Python 和可视化时可缩短；账号、数据提取、口径返工与实际试用需要预留时间。以下是工作量估计，不是完成承诺。

| 阶段 | 预计投入 | 工作内容 | 本阶段必须留下的证据 |
| --- | --- | --- | --- |
| 1. 问题与范围 | 4–6 小时 | 明确用户任务、成功标准、P0/P1/P2、风险假设 | PRD、需求池、优先级理由 |
| 2. 数据探查与指标 | 8–10 小时 | 核验字段、事件、空值和样本量；冻结 12 项口径 | 数据 profile、指标字典、数据契约 |
| 3. 数据模型与处理 | 10–14 小时 | SQL 建模、质量规则、幂等运行、日志与对账 | SQL、模型图、质量报告、运行记录 |
| 4. 产品实现 | 10–14 小时 | 原型、4 页界面、筛选下钻、口径展示与导出 | 原型、运行产品、交互说明 |
| 5. 业务分析 | 6–8 小时 | 完成两期对比、漏斗及分层分析，形成证据和建议 | 3 条发现、SQL、分析报告、验证方案 |
| 6. 验收与迭代 | 8–12 小时 | 质量与业务验收、故障演示、真实试用、修复问题 | UAT、反馈记录、问题闭环、版本记录 |
| 7. 展示与复现 | 4–6 小时 | 干净环境复跑、录像、整理项目入口与发布材料 | 运行指南、演示录像、发布清单 |

三个里程碑：

1. M1：能从固定数据快照复算核心指标；数据口径及质量问题已记录。
2. M2：业务使用者能在产品中完成查询、诊断和导出；关键数字可追溯。
3. M3：完成验收、问题修复、复跑和展示；明确仍未验证的部分。

## 11. 数据质量与异常闭环

至少实现以下 20 项检查。每项有结果、阈值、严重级别、处理方式和日志；样本本身的问题允许作为已知限制保留，不通过随意删数制造“全绿”。

| 编号 | 检查内容 |
| --- | --- |
| Q01 | 快照日期范围与清单一致 |
| Q02 | 必需字段存在，类型与数据契约一致 |
| Q03 | 空用户标识占比被统计与展示 |
| Q04 | 空会话 ID 占比被统计与展示 |
| Q05 | 日志或快照的重复导入不产生重复结果 |
| Q06 | 标准化前后事件数差异有解释 |
| Q07 | 交易 ID 重复与冲突有记录 |
| Q08 | 交易归属到用户、会话的关联规则明确 |
| Q09 | 会话表组合键唯一 |
| Q10 | 主漏斗时间顺序符合规则 |
| Q11 | 同一闭合漏斗各阶段人数单调不增 |
| Q12 | 比率分子分母范围一致，分母为零有处理 |
| Q13 | 交易金额缺失、币种与金额覆盖率明确 |
| Q14 | 商品展开没有放大订单级金额 |
| Q15 | 汇总金额与同范围合格交易明细对账 |
| Q16 | 用户分层互斥且集合完整 |
| Q17 | 筛选后页面、导出和 SQL 复算一致 |
| Q18 | 不完整比较区间与回访观察窗口被识别 |
| Q19 | 任务失败时不会发布半成品或覆盖成功版本 |
| Q20 | 指标版本、数据版本及运行日志能够对应 |

演示三个受控异常：

1. 在测试副本注入一条重复交易或冲突金额，展示检测、隔离和对账。
2. 删除一个测试日期分区，展示断档告警及补跑恢复。
3. 注入空会话 ID 或模拟刷新失败，展示覆盖率变化、告警与旧版本保留。

每个案例记录：现象 → 检查命中 → 数据来源与加工步骤 → 处理决策 → 复跑 → 验证 → 关闭。异常注入只操作测试副本，不改写官方原始快照。

## 12. 业务验收与独立交付证据

### 10 条基本验收用例

1. 选择完整周期，页面指标与对应 SQL 结果一致。
2. 筛选设备后，所有受支持图表和导出同步变更。
3. 口径卡片能解释分子、分母、日期字段、来源和版本。
4. 用户能够找到漏斗损失最多的阶段，并查看样本量。
5. 用户能区分普通会话购买转化与闭合漏斗转化。
6. 无数据时显示原因，不将空值伪装为零。
7. 用户分层总量可以按相同范围复核。
8. 数据或任务异常可以在运营页发现，并查看处理记录。
9. 导出包括筛选条件、版本及数据范围，并与页面对账。
10. 按 README 在干净环境复跑，可得到同一快照、同一口径的结果。

技术验收由自己完成并保留执行证据；用户验收邀请至少一名真实试用者，推荐两名。记录匿名角色、日期、任务、操作结果、遇到的问题与修改。不要将自己假设的用户意见写成访谈结论。

适合交付的证明链：

| 工作环节 | 对应的可追溯材料 |
| --- | --- |
| 理解业务与需求 | 问题定义、用户任务、需求与功能对应表 |
| 做取舍 | P0/P1/P2、被延后需求及理由、变更记录 |
| 定义数据 | 指标字典、粒度、模型图、数据契约 |
| 设计产品 | 页面原型、交互规则、空态与异常态 |
| 推动实现 | 里程碑、提交记录、问题清单及进度记录 |
| 验收交付 | UAT、对账、性能报告、发布清单 |
| 持续迭代 | 真实反馈 → 修改 → 复验的对应记录 |

项目记录覆盖本地开发与验证；生产运营、协作过程及商业效果需另行验证。

## 13. 预估效果与可报告结果

以下数字为验收目标。只有实际验证的结果才纳入项目成果记录。

| 维度 | 目标 | 如何测量 |
| --- | --- | --- |
| 功能完整性 | 12 个指标、4 个页面均有定义与验收证据 | 逐项核对注册表、产品与 UAT |
| 数据质量 | 至少 20 条规则均执行，有异常解释或阻断策略 | 保存每次检查结果及问题处置 |
| 一致性 | 核心指标在同口径 SQL、页面、导出间一致 | 同一快照与筛选条件对账；金额精度容差预先声明 |
| 分析价值 | 3 条可复算发现、对应建议与验证设计 | 每条附 SQL、图表、样本量和局限 |
| 页面响应 | 本地汇总数据常用交互，预热后 p95 目标不高于 3 秒 | 固定硬件与数据范围，每项至少 20 次测量；冷启动另报 |
| 稳定性 | 同一快照重复执行，核心结果不变 | 比较模型行数、主键集合和汇总指标 |
| 故障处理 | 3 个受控案例能发现并记录；至少完成一次修复复跑 | 提供日志、问题记录、前后结果 |
| 易用性 | 真实试用者能够独立完成核心任务 | 记录任务成功率、耗时及反馈；按实际人数报告 |

若要写“取数效率提升”，先制定同一任务集，采用合理的手工 SQL / Excel 流程与产品流程分别计时。每项至少重复 3 次，说明参与者、熟悉程度、缓存和任务范围。结论只能表述为“本次任务测试中节省时间”，不能外推为企业团队效率提升。

项目可以证明发现问题、分析差异、缩短测试任务的操作路径。真实转化率、成交额、留存的提升需要业务干预和实验，本项目不预设这类结果。

### 三项业务分析的建议落点

1. 金额变化：在同一金额完整交易集合上，将已记录购买金额变化分解为交易量与客单价变化。可以采用对称分解：数量贡献为 `(N1-N0)×(A0+A1)/2`，客单价贡献为 `(A1-A0)×(N0+N1)/2`，两项应精确加回金额差异。`N` 是金额完整交易数，`A` 是同一集合客单价。
2. 转化变化：比较设备构成与各设备内的会话转化，检查总体变化是否来自流量结构改变；保留未知设备、小样本和数据覆盖率。
3. 行为路径：比较严格漏斗各阶段的损失与窗内购买分组，提出具体核查或实验建议；埋点缺失和时间顺序不确定需要先排查。

以上是分析方向。若样本未体现预期差异，应如实报告“差异不明显”或改选有业务意义的可比问题，不为凑结论挑选极端日期。
